# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`multi` is a C++17 real-time threading framework distributed as a single static library. It's designed to be vendored (submodule / `add_subdirectory`) into a parent project; its tests and benchmarks only build when `multi` is the top-level CMake project.

## Build / test / bench

In-source builds are blocked by [CMakeLists.txt](CMakeLists.txt) — always use a separate build dir. As the top-level project with a single-config generator, multi defaults an unset `CMAKE_BUILD_TYPE` to Release; vendored, it leaves the parent's build type alone, and multi-config generators (Visual Studio, Ninja Multi-Config) get no `CMAKE_BUILD_TYPE` at all.

```sh
# Library + tests (default when standalone)
cmake -B build
cmake --build build
ctest --test-dir build --output-on-failure

# Run a single test by Catch2 name. ctest sees them with the "(multi) " prefix
# from catch_discover_tests; the binary itself takes the raw TEST_CASE name.
./build/test-multi "Context: range int"
./build/test-multi -# "[some-tag]"

# Benchmarks (built by default when standalone, like the tests)
cmake -B build -DMULTI_BUILD_BENCHMARK=ON
cmake --build build
./build/bench-multi "[fast]"       # ~10s subset
./build/bench-multi "[slow]"       # mandelbrot, imbalanced
./build/bench-multi --benchmark-samples=20
./build/bench-multi --reporter xml --out before.xml

# Run + speedup summary table (forwards filters/flags to bench-multi).
# Cross-platform: resolves the .exe suffix and multi-config build/<Config>/ paths.
python bench/report.py "[fast]"

# Record a run to JSON, or append it to a rolling history file.
python bench/report.py "[fast]" --json-out build/bench-latest.json
python bench/report.py "[fast]" --json-append build/bench-history.json

# Compare this run against the latest values in a history/run JSON, then
# extend that history in the same invocation (regression tracking).
python bench/report.py "[fast]" --compare build/bench-history.json \
                                --json-append build/bench-history.json
```

**Benchmark layout**: each workload is its own translation unit under [bench/](bench/) — `empty_tasks` / `mandelbrot` / `tiny_tasks` / `imbalanced` / `nested` / `async_latency` / `async_fanout` / `heavy_capture` / `steal_contention` / `each_iter` / `parallel_pair` / `recipe`, each listed explicitly in [CMakeLists.txt](CMakeLists.txt) and sharing [bench/workloads.h](bench/workloads.h). `recipe` pairs `run / …` sections (a `multi(recipe)` row against an `async(baseline)` row doing the same DAG with explicit `async` + `waitAll`) with `build / …` sections whose only row, `recipe(build)`, times graph construction alone and has no baseline. The header holds the `bench::` dispatch adaptors (`baseline` / `items` / `chunks` / `invoke_multi`), the `Graph` helper for mandelbrot, and the `chunkCount(count)` helper that mirrors `multi::Auto`. `items` passes `multi::PerItem` explicitly, and so do `each_iter`'s `multi(items)` rows, because the policy-less `each`/`range` chunk like `multi::Auto`; keep it explicit so every `multi(items)` row stays one task per item and comparable with recorded history. The `CHUNK_FACTOR` (= 4) oversubscription constant lives in [include/multi/chunkpolicy.h](include/multi/chunkpolicy.h) (the single source of truth); `chunkCount` consumes `multi::CHUNK_FACTOR`. When adding a workload, add a new `.cpp` plus its CMakeLists entry; don't reintroduce a monolithic `workloads.cpp`. Conventions to preserve: BENCHMARK labels are `impl(variant)` with no space (`serial(baseline)`, `async(baseline)`, `multi(items)`, `multi(chunks)`, `multi(parallel)`, `multi(async)`, `multi(range)`, `multi(recipe)`, `recipe(build)`) and size/shape lives in the TEST_CASE/SECTION name; [bench/report.py](bench/report.py) keys its speedup column off the variant that ends in `(baseline)` in each (workload, section) group, so baselines must stay named `…(baseline)`. Keep thread creation out of timed `BENCHMARK` bodies — `steal_contention` spawns its driver threads once via a persistent `DriverPool` released per sample, so OS thread-lifecycle cost doesn't swamp the measurement.

**`bench/report.py` JSON + comparison**: beyond the plain speedup table, `report.py` takes `--json-out <path>` (writes this run as a single-run snapshot — git metadata + flattened `benchmarks[]` at top level), `--json-append <path>` (appends the run to a `{schema_version, runs:[…]}` history file, creating it if absent), and `--compare <path>` (diffs the current run against the latest value per `(workload, section, variant)` key in a history/run JSON). The three combine — `--compare … --json-append …` is the regression-tracking loop. Each run captures git `commit`/`short_commit`/`branch`/`dirty`. The comparison table adds `PREV`/`DELTA%`/`SIGNAL` columns alongside the same speedup column, where `SIGNAL` is a σ estimate (`|Δmean| / hypot(sd, prev_sd)`) bucketed `noise (<1) / weak (<2) / clear (<3) / strong (≥3)` and ANSI-colored red=slower / green=faster (color gated on tty, suppressed by `NO_COLOR` or `TERM=dumb`). Rows are sorted deterministically, baseline-first within each group. This mirrors the equivalent tooling in the sibling `archimedes` repo, minus that repo's baseline-less layout — multi keeps the speedup column throughout.

## Architecture

Three layers, public → private:

1. **Free functions** in [include/multi/multi.h](include/multi/multi.h) — `multi::start/stop/threadCount/async/parallel/each/range/waitUntil/waitAll/waitAny`, `async` including the `async(Recipe&&)` overload — thin templates and inline functions (bodies in [include/multi/details/multi.inl](include/multi/details/multi.inl)) that forward to the process-global `Context&` returned by `multi::context()`. That global is a function-local static defined in [src/multi.cpp](src/multi.cpp); there is no setter. Tests exercise multiple `Context` instances by constructing local `multi::Context` objects and calling methods on them directly (never through the global) — preserve that capability when changing `Context`'s interface.

2. **`Context`** ([include/multi/context.h](include/multi/context.h), [include/multi/details/context.inl](include/multi/details/context.inl), [src/context.cpp](src/context.cpp)) owns one `WorkerPool` and implements the dispatch primitives. Templates live in the `.inl`; the non-template members (`start`/`stop`/`threadCount`, `async(Recipe&&)`, `tryRunSteal`) live in the `.cpp`. The wait loops' backoff, `details::WaitBackoff`, has its own [details/waitbackoff.h](include/multi/details/waitbackoff.h) and [src/waitbackoff.cpp](src/waitbackoff.cpp).

3. **`WorkerPool`** ([include/multi/details/workerpool.h](include/multi/details/workerpool.h), [src/workerpool.cpp](src/workerpool.cpp)) owns N `Worker`s, each with its own [`WorkStealDeque`](include/multi/details/workstealdeque.h) + mutex + condvar + thread, all cache-line aligned.

**Namespace convention**: the public API lives in `multi::` — `Context`, `Handle<T>`, `ChunkPolicy` (with `Auto` / `PerItem` / `Serial` / `CHUNK_FACTOR`), `Recipe`, `Step`, `StepLink`, `RecipeResult`, `RecipeHandle`, and every free function in [multi.h](include/multi/multi.h). Every internal type — `Job` and its subclasses, `AsyncJob`, `Task`, `WaitBackoff`, `WorkerPool`, `Worker`, `WorkStealDeque`, `ChaseLevDeque`, `MpmcQueue`, `OperationLock`, `RecipeJob`, `RecipeGraph`, `RecipeStep`, `RecipeSuccessors` — lives in `multi::details::`. Tests and benchmarks that exercise internals qualify accordingly (`multi::details::WorkStealDeque`). When adding a new internal type, put it in `multi::details::`; never extend `multi::` with anything users shouldn't autocomplete. Give it its own header under [include/multi/details/](include/multi/details/), with a matching `src/<name>.cpp` for any non-template code: the public headers (`context.h`, `handle.h`, `multi.h`, …) include details headers but never declare `multi::details` types themselves.

### WorkStealDeque composition

`WorkStealDeque` is two lock-free primitives stitched together, no mutex:
- A fixed-capacity Chase-Lev SPMC deque ([`ChaseLevDeque<Task, LOCAL_CAP>`](include/multi/details/chaselevdeque.h), `LOCAL_CAP = 256`) — owner pushes/pops at the bottom, any thread steals from the top. Per-slot sequence atomics gate slot reuse: the owner's `tryPushBottom` waits for the previous occupant to release the slot before overwriting, which is what makes claim-first stealing safe for move-only `Task`. Released to position `b` after a pop, position `t + Capacity` after a steal — pop reuses the same slot, steals don't.
- A bounded MPMC ring ([`MpmcQueue<Task, OVERFLOW_CAP>`](include/multi/details/mpmcqueue.h), `OVERFLOW_CAP = 4096`) — Vyukov sequence-numbered ring used for spillover and external submits. Visible to stealers as a fallback so externally-submitted work isn't trapped behind a busy owner.

`pop()` refills local from overflow when local size drops below `REFILL_LOW=16` (up to `REFILL_BATCH=32` items), then pops local LIFO; falls through to draining one from overflow when local is empty. `steal()` tries local Chase-Lev first, then overflow.

### Scheduling model

- **Submit routing**: `submit`/`submitBatch` push through `pushOrRun`, which compares `std::this_thread::get_id()` against the target `Worker::thread.get_id()` to detect whether the caller owns that deque. If the round-robin target is the calling thread, the task goes via `WorkStealDeque::tryPushLocal` (Chase-Lev SPSC fast path, no MPMC contention); otherwise via `tryPushRemote` (overflow ring). Whom to wake is decided after the push, by the parking protocol (see Wakeup correctness): with no worker parked a push costs one fence and one relaxed load, with no lock and no notify; otherwise the target is woken if it is parked, and if it is busy, or the push was the owner's own local push, one other parked worker is woken to steal it. Thread-ID comparison is correct across multiple pool instances — an index-based check would misidentify workers from a different pool sharing the same slot index.
- **Operation guard**: `submit`/`submitBatch`/`tryStealAny` acquire a slot via `std::unique_lock<OperationLock>(m_opLock, std::try_to_lock)`. `OperationLock` ([include/multi/details/operationlock.h](include/multi/details/operationlock.h)) packs an active flag (high bit) and in-flight counter (lower bits) into one `atomic<size_t>`. `try_lock` does `fetch_add(1, seq_cst)` and backs out if the active bit was not set; `unlock` decrements. `deactivate()` clears the active bit (`fetch_and(~bit, seq_cst)`) then spins until the full word reaches zero. The Dekker-style seq_cst on both sides ensures: either `try_lock` sees the cleared bit (bails) or `deactivate` sees the incremented count (waits) — `m_workers` remains valid for the full duration of any held slot.
- **Full-deque policy**: `pushOrRun` tries the push once (SPSC path for the owner, MPMC overflow ring for others). If the deque is full it runs the task inline on the submitting thread instead of spinning — the caller becomes a cooperative participant under back-pressure. `WorkerPool::trySubmit(Task&)` is the variant that never runs the task: it queues and wakes like `submit`, or returns false with the task untouched when the pool is not running or the target deque is full (`tryPush`), leaving the caller to run it. `RecipeJob` schedules through it, because it must not nest.
- **Local pop**: LIFO from the back of the owner's local Chase-Lev (temporal locality preserved).
- **Steal**: FIFO from the front of another worker's local Chase-Lev (then its overflow ring as a fallback), scanning `(self+1) % N … (self-1) % N` to spread contention.
- **Caller participation**: `Context::runQueueJob` (used by `parallel`/`each`/`range`) waits for `remaining()` to reach zero while running stolen tasks via `Context::tryRunSteal`, so the calling thread is an active participant — `bench/main.cpp` deliberately starts `hw-1` workers to leave room for the caller. **`Handle::wait` does NOT participate in stealing** — `Handle` is Context-agnostic and blocks plainly. Callers that want to help drain the pool while waiting on a specific async result call `Context::waitAll(handle)` (single-arg variadic) explicitly. The underlying public primitive is `Context::waitUntil(pred)`; `waitAll`/`waitAny` are thin wrappers over it (`waitAny` uses a left-fold over `||` plus a manual index counter so it can return the first-complete handle's source-order index). `waitUntil` and both of `runQueueJob`'s wait loops are one private helper, `Context::stealUntil(done)`: call `tryRunSteal` until `done()` is true, resetting a `details::WaitBackoff` on every successful steal and letting it yield or sleep after every failed one (see Waiter backoff). This split exists so a plain `Handle::wait()` can block without taking on the obligation to run stolen work — useful when you need deterministic completion ordering, e.g. pre-completing one handle before `waitAny` without pulling its siblings inline — and so the cross-context handle-passing story works. Trade-off: a task that submits nested work and blocks on it with a plain `Handle::wait()` needs another thread to run that work. The push wakes a parked worker to steal it, so it is no longer stranded while other workers sleep; it still deadlocks when no other thread can take it — on a 1-worker context, or when every worker is blocked the same way — unless some thread is stealing in a `waitAll`/`waitUntil`. Inside a task, wait with `waitAll(handle)`, which can run the nested task itself. (Self-healing before the typed-Handle refactor made `wait()` plain; intentional change.)
- **Waiter backoff**: `details::WaitBackoff` and its constants are in [details/waitbackoff.h](include/multi/details/waitbackoff.h); its clock check and sleep are in [src/waitbackoff.cpp](src/waitbackoff.cpp). While there is nothing to steal, a waiter yields between attempts for `WAIT_SPIN_TIME` (20 ms), reading `steady_clock` only every `WAIT_CLOCK_INTERVAL` (64) failed attempts, so a short wait never reads it. After that it sleeps between attempts, from `WAIT_SLEEP_MIN` (50 µs) doubling to `WAIT_SLEEP_MAX` (1 ms); any successful steal goes back to spinning. The trade: a long wait burns about 20 ms of a core instead of the whole wait, and in exchange notices completion, or new work to steal, up to one sleep late — `WAIT_SLEEP_MAX` plus the sleep's slack. Linux, Android, macOS and iOS sleep with `sleep_for` (slack of tens of µs). On Windows `sleep_for` rounds up to the system timer tick (~15.6 ms), so the sleep — `details::preciseSleep`, in [src/platform.cpp](src/platform.cpp) — uses a high-resolution waitable timer (`CreateWaitableTimerExW` with `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`), which leaves the process's timer resolution alone: one per thread, created at the thread's first such sleep and closed at thread exit by `thread_local` destruction (a thread is in at most one sleep at a time). Measured on Windows 11 / Ryzen 9 5950X, a backed-off waiter noticed completion at worst 1.56 ms late with the timer against 15.1 ms with `sleep_for`. If the timer cannot be created (before Windows 10 1803), armed, or waited on, the sleep falls back to `sleep_for` and so to one tick. `WAIT_SPIN_TIME` is longer than every benchmark wait and a 60 Hz frame, so only genuinely long waits ever sleep. The `count == 0` / `count == 1` paths of `runQueueJob` never wait, so `multi::Serial` never steals or sleeps.
- **Single-threaded mode**: `WorkerPool::submit` / `submitBatch` run tasks inline on the caller when `!isActive()` — code written for the multi-threaded API works unchanged with no pool started. `each(chunkPolicy, …)` and `range(chunkPolicy, …)` also short-circuit to a serial loop when the resolved count `<= 1`.

`WorkStealDeque::localSizeHint()` and `overflowSizeHint()` expose the two halves separately, for routing diagnostics and for `tryGetTaskBeforePark`'s relaxed emptiness reads.

### Wakeup correctness

Workers sleep under the parking protocol spelled out in the "Parking protocol" comment above `workerMain` in [src/workerpool.cpp](src/workerpool.cpp); read it, and the comment in `tryGetTaskBeforePark`, before changing any wake or park path. In outline:

- **Parked state**: each `Worker` has an `atomic<bool> parked`, written only under that worker's mutex, and the pool counts the parked workers in `m_parkedCount` (own cache line). A worker sleeps in `cv.wait` only while registered as parked, never unregistered, and holds its mutex from registering until `cv.wait` releases it.
- **Worker side** (`workerMain`): when its drain loop's last scan comes up empty it registers at once (`parked = true`, `++m_parkedCount`), issues a seq_cst fence, and re-checks the deques with `tryGetTaskBeforePark`; only if that finds nothing does it `cv.wait` (no predicate — the loop re-checks after any wake). After a wake that claimed it, it first does a plain `tryGetTask` scan, so it takes the task it was woken for without touching the shared count, and registers again only if that fails. Leaving with work, or for stop, while still registered, it unregisters itself.
- **Submitter side**: after pushing, `submit` and `trySubmit` call `wakeAfterPush(idx)`, which starts with `anyParkedAfterPush()` — a seq_cst fence, then a relaxed read of `m_parkedCount`. Zero: done, no lock, no notify. Otherwise it claims and wakes the target with `workerNotify(target)` if the target is parked; if the target is busy, or the push was the owner's own local push, `wakeOneParked` claims and wakes one other parked worker to steal the task. `submitBatch` fences once per batch, then claims each parked worker among the first `min(count, workers)` target slots and wakes one other parked worker per target slot that is busy or is the caller's own.
- The two fences make push-versus-park a Dekker pair: either the worker's re-check sees the push, or the submitter's read of the count sees the worker parked and wakes it or another parked worker. A worker's `+1` and `-1` on the count both happen under its own mutex, so the count never under-reports a registered worker.
- **`workerNotify` is the only wake site**: lock the worker's mutex, claim it if parked (clear `parked`, decrement the count), unlock, then `notify_one` only if it claimed; it returns whether it did. Because a parked worker holds its mutex until `cv.wait` releases it, a claimer that sees `parked == true` under the lock has found it inside `cv.wait`, so the notify cannot be lost; one that sees `false` has found a worker that is not waiting and needs no notify. Claims are exclusive, so two pushes that each need a helper wake two workers, not one twice.
- **`tryGetTaskBeforePark` is one pass** over every deque, own first. A deque that reads non-empty (overflow half first, then local) is retried until a take succeeds or it reads empty, which covers a Chase-Lev steal that lost its CAS and an MPMC slot claimed but not yet filled; an empty deque is skipped on the relaxed size reads. It must **not** wait for every deque to read empty: a version that did kept idle workers awake through a caller's batch push, taking each task as it landed and contending with the pusher, and slowed the 50k-task `multi(items)` rows of `empty_tasks`, `heavy_capture` and `each_iter` by roughly 25–50%. One pass is enough because a task the pass misses was pushed after the worker's fence, so its submitter's count read sees the worker parked.

`m_opLock.isActive()` is the pool liveness check: the worker's loop leaves on a task or on `!isActive()`, and `stop()` calls `deactivate()` then `workerNotify` on every worker — parked ones are claimed and woken, and one that is not parked is not waiting and sees `!isActive()` the next time it takes its mutex. Workers swallow exceptions from raw `submit`d tasks so a throw can't kill the worker thread.

Cost of the protocol, measured with the benchmarks against the scheduler before it (Windows 11, 31 workers): `steal_contention` about +4–5%, the 1k-task `multi(items)` rows about +5% and `parallel_pair / 1k` +2–4%; the 50k-task rows are unchanged.

### Job dispatch

`parallel`/`each`/`range` each construct a typed `Job` subclass that owns the dispatch state for one call; `async` constructs an `AsyncJob`, which is not a `Job`. All of them live in [include/multi/details/job.h](include/multi/details/job.h):
- `RangeJob<IDX,FUNC>` — index-only dispatch, no per-task storage. Chunk slice bounds are computed inside `run(i)` from `(begin, step, base, extra)`. Serves both chunked and per-index dispatch: plain `range(begin, end[, step], func)` forwards to the chunked overload with `multi::Auto`, and `multi::PerItem` resolves to one chunk per index (`m_base==1`, `m_extra==0`), so `run(i)`'s slice loop runs exactly once over `begin + i*step`. (There used to be a separate non-chunked `RangeJob`; an A/B over `empty_tasks`/`tiny_tasks`/`each_iter`/`heavy_capture` showed no measurable runtime cost from routing per-item through the chunked job, so the two-template split was collapsed into this one.)
- `EachJob<ITER,FUNC>` — iterator-category split via `if constexpr`: random-access iterators (vector, array, raw pointers) store the begin iterator directly with no allocation; other categories (std::map, std::list, etc.) materialise a `std::vector<T*>` pointer table at construction. Indexed via `m_storage[startIdx+k]`. Like `RangeJob`, serves both chunked and per-item dispatch: `each(begin, end, func)` and `each(container, func)` forward to the chunked overload with `multi::Auto`, and `multi::PerItem` gives one chunk per item.
- `ParallelJob<Fs...>` — `std::tuple<Fs...>` plus an index-pack fold-expression dispatcher.
- `AsyncJob<F,R>` — **not a `Job`**: a standalone, non-copyable class holding only `std::promise<R>` + the user functor, with no countdown and no captured exception, because its result or exception goes through the promise and it never passes through `runQueueJob`. Heap-allocated via `shared_ptr` (lifetime extends past the calling stack frame). Templated on the user functor's return type `R = invoke_result_t<F>` (defaults via second template arg). `run()` takes no index; the void / non-void split is an `if constexpr` inside it. Backs the typed `Handle<R>` returned by `Context::async`.

The base [`Job`](include/multi/details/job.h) is non-polymorphic — no virtual `run`, protected non-virtual destructor. It only holds the shared state: `m_taskCount` (immutable), `m_remaining` (atomic countdown), `m_excOnce`/`m_firstException` (exception capture), plus the `runOne(F&&)` template helper that wraps user code with try/catch + release-`fetch_sub`.

`Context::runQueueJob<JobT>(JobT&)` is templated on the concrete subclass so `job.run(i)` is a direct call resolved at compile time, not a vtable hop. Four paths:
- `taskCount() == 0`: no-op.
- `taskCount() == 1`: run inline on caller (covers historical `taskCount<=1` serial fallback for chunked jobs, and any single-task dispatch).
- `taskCount() == 2`: submit task 0 to a worker via `submit(Task)`, run task 1 inline on the caller, then wait for task 0 via `stealUntil(remaining() == 0)`. The `parallel(a, b)` fast path — saves one push + `workerNotify` + steal-loop iteration vs the generic submitBatch path. Measured `~−40%` on the dispatch-heavy `parallel_pair / 1k rounds` bench; neutral on recursive workloads with non-trivial per-leaf work.
- `taskCount() >  2`: submit a batch via `WorkerPool::submitBatch(count, gen)` (the generator-based overload — no intermediate `vector<Task>`), wait via `stealUntil(remaining() == 0)`, stealing while it waits, then `rethrowIfFailed()`.

Wrapper Tasks pushed into worker deques are `[&job, i]() { job.run(i); }` (16 B, inside `Task`'s 24 B SBO) for sync jobs; AsyncJob's wrapper is `[job]() { job->run(); }` capturing the `shared_ptr` by value (also SBO). Sibling tasks are **not** cancelled on exception — the surviving `runOne` calls still decrement `m_remaining`.

`async` ([context.inl](include/multi/details/context.inl)) creates the `shared_ptr<AsyncJob<F,R>>` (with `R = invoke_result_t<F>`), grabs a `std::future<R>` from its promise, submits the wrapper, and returns `Handle<R>`. `Handle` is a class template — `template<class T = void> class Handle` — so CTAD makes `auto h = multi::async([]{ return 42; });` deduce `Handle<int>`; the default-init form is `multi::Handle<> h;` (void default). `Handle` wraps a `shared_future<T>` and exposes only five operations: `complete()` (non-blocking ready check; also true for an invalid handle), `valid()` (has shared state), `wait()` (plain block until ready — **no** steal participation, does not rethrow), `bool get(U* out)` (non-blocking copy-out; `U` defaults to `T` and must be assignable from `const T&` — returns `false`, leaving `*out` alone, if not yet complete or the handle is invalid (default-constructed, moved-from or taken), otherwise copy-assigns the value and returns `true`, rethrowing a stored exception; idempotent via `shared_future`), and `bool take(T* out)` (non-blocking move-out, for every non-void, non-reference `T` including move-only ones — the same `false` cases; on success it moves the result into `*out` and resets the handle, as if moved-from: `valid()` false, `complete()` true, later `get`/`take` return `false`; if the task threw it rethrows and leaves the handle valid, so a later call rethrows again; it takes a `T*` exactly, a `static_assert` requires `T` non-const and move-assignable, and it is not safe while another thread uses the same Handle). `get(&out)` on a result it cannot copy-assign is a `static_assert` that names `take()` — chosen over SFINAE, which would leave only a generic "no matching overload" error; the trade-off is that detection idioms still see `get` as callable for a move-only `T`, so generic code should call `take`. `Handle<void>` has neither of those two: it has `bool get()` (non-blocking; `false` if not complete or invalid, otherwise `true`, rethrowing a stored exception) and no `take`. A reference `T` keeps only `get`. **`Handle` holds no Context pointer** and `wait()` blocks plainly; to help drain the pool while waiting, call `Context::waitAll(handle)` (or the `multi::waitAll(h)` free-function). Handle's templated method bodies live in [details/handle.inl](include/multi/details/handle.inl); there is no `handle.cpp`. **`Handle` is move-only and its destructor does not block** — there is no `operator=`, `detach()`, `wait_for`/`wait_until`, or blocking `get()`; dropping a handle does not wait (the task still runs on the pool and is guaranteed complete once `stop()` drains the workers). A failed task's exception surfaces only through `get(&out)`, `take(&out)`, or `Handle<void>::get()`; `wait()` never rethrows.

**Inlining trade-off, documented:** templating `runQueueJob` lets the compiler see through every layer, which is great for `tiny_tasks/items`-shape workloads (~5–15% improvement vs the original mutex deque) but produces large per-instantiation wrapper functions for chunked jobs whose user lambdas have heavy captures. `heavy_capture`'s chunked rows show a measurable regression vs the mutex baseline at high chunk counts; the wrapper Task `invoke()` ends up at 4–11 KB after the user's body inlines through `RangeJob::run` → `runOne` → chunk loop. `[[gnu::noinline]]` doesn't recover it (the user lambda still inlines into `run` itself). Real CPU-bound workloads (mandelbrot, imbalanced) sit at noise. The trade is intentional — don't try to "fix" it by re-virtualising `Job::run` without re-checking the items rows.

### Recipe

An execution-only DAG: callers add void steps, order them, and launch the whole graph once; data movement stays in the caller's own model. Public side, in `multi::`: `Recipe`, `Step`, `StepLink`, `RecipeResult` in [include/multi/recipe.h](include/multi/recipe.h) ([src/recipe.cpp](src/recipe.cpp)) and `RecipeHandle` in [include/multi/recipehandle.h](include/multi/recipehandle.h) ([src/recipehandle.cpp](src/recipehandle.cpp)). Internal side, in `multi::details::`: `RecipeStep` / `RecipeSuccessors` / `RecipeGraph` in [details/recipegraph.h](include/multi/details/recipegraph.h) and the executor `RecipeJob` in [details/recipejob.h](include/multi/details/recipejob.h) + [src/recipejob.cpp](src/recipejob.cpp). The domain vocabulary is in [CONTEXT.md](CONTEXT.md), the decision in [docs/adr/0001-add-execution-only-recipe.md](docs/adr/0001-add-execution-only-recipe.md), and the construction-cost work in [docs/perf-investigation-2607.md](docs/perf-investigation-2607.md).

- **Building**: `recipe.step(f)` stores a void callable as a `details::Task` (so move-only captures work) and returns a `Step`, a 32-bit index token; a default `Step`, or the one `step()` returns once the index space is exhausted, is invalid (`valid()` / `operator bool`). `recipe.order(a >> b)` (`operator>>` builds a `StepLink`) adds an edge and returns a `RecipeResult` — `Ok`, `InvalidStep`, `WouldCycle` (a self-link included) or `DuplicateEdge`; setup errors are results, never exceptions. The cycle check is skipped while every accepted edge, and the new one, goes from a lower step index to a higher one (`m_stepsAreTopologicallyOrdered`); otherwise it is a reachability DFS over reusable, generation-marked scratch buffers. Duplicate detection switches to a per-step `unordered_set` once a step has 128 successors, and `RecipeSuccessors` stores the first four successors inline before spilling to a vector. `Recipe` is move-only.
- **Launch**: `Context::async(Recipe&&)` in [src/context.cpp](src/context.cpp) (and its `multi::async(Recipe&&)` forwarder) bakes the recipe into a `RecipeGraph`, moving the steps out, builds a `shared_ptr<RecipeJob>` whose submit callback is `WorkerPool::trySubmit`, calls `start()`, and returns a `RecipeHandle` holding a `Handle<>` on the job's `std::promise<void>` plus the job pointer, for progress.
- **Running**: per step, `m_pending` counts unfinished predecessors and `m_state` moves `Pending → Scheduled → Finished` by CAS. `start()` scans for roots (pending count 0) in index order and submits each. A runner runs the step's callable, marks the step Finished and counts it (`finishOne`). On success it decrements every successor's pending count, submits each successor that became ready except the first, and continues inline with that first one (`runChain`). Each submitted task is `[self = shared_from_this(), index]`, 24 B on 64-bit, so an SBO fit. If the callable threw, the first exception is kept and `skipSuccessors` claims every transitive successor still `Pending` (CAS `Pending → Finished`, so two failing steps skip a shared successor once) and counts it without running it. When the count reaches zero, `complete()` sets the promise once — with the first exception if any step failed. An empty recipe completes inside `start()`.
- **`RecipeHandle`**: move-constructible only; copying and assignment are deleted. `complete()` / `valid()` / `wait()` / `bool get()` forward to the wrapped `Handle<>`, so `wait()` does not steal and `get()` is non-blocking and rethrows the first step exception; `stepCount()` / `finishedCount()` / `progress()` read the job, and finished counts succeeded, failed and skipped steps alike, so progress reaches 1.0 after a failure. `multi::waitAll(h)` works on it, since `waitAll` only calls `complete()`.

Invariants to keep:
- **The stack stays flat however large the graph.** `WorkerPool::submit` runs a task inline when the pool is not started, is stopping, or the target deque is full, so a recipe that scheduled through it would nest another `runStep` per submitted successor. `RecipeJob` schedules through `WorkerPool::trySubmit` instead, which queues the task or returns false without running it; `schedule()` then appends the step to the calling frame's deferred-step list, and the outermost runner (`runStep`, or `start()` for roots) works through that list after each chain (`runDeferred`). Keep the `Submit` callback to that contract — it must never run the task — and don't bring back a `thread_local` or any other side channel to detect inline execution: the return value is the whole signal.
- **The deferred list is intrusive**, linked through the step's `m_pending` slot, which is spent once a step is Scheduled (its count reached zero and no predecessor touches it again): deferring allocates nothing and cannot fail. Anything that reads `m_pending` later (diagnostics, progress) must allow for a Scheduled step's slot holding a link; `start()`'s root scan already may read one, which is harmless because a Scheduled step fails `tryMarkScheduled`.
- **Skipping is iterative.** `skipSuccessors` walks with an explicit `std::vector` stack of the steps this thread claimed, and the first successor claimed from each visited step is walked next without being pushed, so skipping a chain allocates nothing. It is `noexcept`: when a push fails, the step that could not be pushed is walked by a nested call, so the walk degrades to recursion at branching steps instead of terminating or dropping a claimed step, which would leave the recipe unable to complete. Don't go back to recursing per step — a long chain whose head throws overflows the stack.
- **Step callables are destroyed once run or skipped, before the step is counted** — by `executeStep` after the callable returns or throws, and by `skip` once it wins the CAS. The release happens-before the final count that completes the promise, so once `wait()` returns no step callable or capture is alive, although the `RecipeHandle` keeps the job for progress. Capture destructors run on the thread that ran or skipped the step.
- **No order is promised between ready steps.** On an inactive pool the roots run in index order, a step's first ready successor continues inline, and the others run FIFO after the current chain; don't write tests that depend on more.
- `RecipeJob` is not a `Job` and doesn't go through `runQueueJob`: like `AsyncJob`, it outlives the launching frame (held by the submitted tasks' `shared_ptr` captures and by the handle) and reports through its promise.

### Type-system invariants

- `RangeJob` takes any arithmetic `IDX` but `bool`: signed, unsigned or floating-point. Unsigned is safe because `computeTotal` returns early on `end <= begin`, so the span can't underflow, and `run(i)` is counted, so nothing wraps at the top of the type. Signed is safe for any span, including one wider than `IDX`'s maximum (next bullet). `begin`, `end` and `step` deduce one type, so `range(0, v.size(), f)` stays a compile error rather than converting a stray `-1` to a huge unsigned value; spell it `range(std::size_t{0}, v.size(), f)`.
- `RangeJob`'s total is computed via the `is_integral_v<IDX>` branch: integer types use `span / step`, rounded up from the remainder rather than with `span + step - 1`, which wraps near the top of an unsigned type (O(1)); floating-point uses an additive loop so the count matches what an equivalent serial loop would produce. A non-positive `step` is an empty range, not a huge total. Integer arithmetic — the span in `computeTotal` and `begin + k*step` in `indexAt(k)` — runs in `std::make_unsigned_t<IDX>`, the unsigned type of `IDX`'s width, where it is exact for any `begin < end` with `step > 0`: the true span fits there, `k*step` stays below it, and the sum lies in `[begin, end)`. So a signed range wider than the type's maximum, e.g. `range(4, INT_MIN, INT_MAX, 1 << 28, f)`, visits exactly the right indices instead of overflowing (UB) in `end - begin`. Narrow types promote to `int` in between, so every intermediate is cast straight back to the unsigned type — keep those casts. The final cast back to a signed `IDX` is modular: implementation-defined in C++17, but what GCC, Clang and MSVC do, and required by C++20. `run(i)` is **counted** — `k` over `[startIdx, startIdx + len)`, dispatching `indexAt(k)` — so the iteration count always equals the total and an index's value doesn't depend on the chunk policy. Don't go back to `j += step` against a computed end: a float chunk drifts to a different count (0 to `24*0.1f` by `0.1f` visited 26 of 25), and the end overflows at the top of `IDX`. For floats the last value may differ by fp rounding from a serial additive loop, but the iteration count matches.
- The chunked `each`/`range` leading argument is a `multi::ChunkPolicy` ([include/multi/chunkpolicy.h](include/multi/chunkpolicy.h)), not a raw `size_t`. It is one of: an exact count (implicit `ChunkPolicy(size_t)`, so `each(64, …)` still compiles), `multi::Auto` (`clamp((workers+1)*CHUNK_FACTOR, 2, total)` — equals the old `bench::chunkCount`, and the default when no policy is given), `multi::PerItem` (one task per item), or `multi::Serial` (one task). **`Serial` carries a promise the others don't: every item in order, on the calling thread, with nothing else run on that thread meanwhile, and a throw ends the walk there.** It adds no dispatch path; resolving to 1 sends it through `runQueueJob`'s `count==1` inline path, which submits nothing and never steals. Consumers depend on the order (lain's `ExecutionPolicy::DeterministicDebug`), and the `Context: … Serial …` cases in [test/context.cpp](test/context.cpp) pin it on a started pool. It resolves to a concrete count via `ChunkPolicy::resolve(total, workerCount)`, called inside the chunked Jobs' `makeSetup` where `total` is already known. **`workerCount` is passed in from `Context::threadCount()`** — the Job must never read the process-global context, or local-`Context` tests would resolve `Auto` against the wrong pool. `PerItem` is not a separate fast path: it resolves to `total` (one chunk per item, `m_base==1`) — `EachJob`/`RangeJob` are the single Job per family that handle both chunked and per-item dispatch. The policy-less `each`/`range` overloads forward to the `ChunkPolicy` overload with `multi::Auto`; the default is set in exactly two places in [context.inl](include/multi/details/context.inl), the iterator-pair `each` and the stepped `range`, which the other policy-less overloads reach. Against one task per item, callers see a difference only once `total` exceeds `(workers+1)*CHUNK_FACTOR`: a throw ends the rest of its chunk (the items after it in that chunk are skipped, every other chunk still runs, and the first exception is still rethrown at the end), consecutive items run in order on one thread (so items that block on each other can deadlock within a chunk, and `thread_local` state is shared across it), and balancing is per chunk. On an inactive context `Auto` resolves to `min(4, total)` chunks, which run inline one after another, so items still run in order on the caller. The `CHUNK_FACTOR` constant lives in chunkpolicy.h and is the single source of truth (bench consumes `multi::CHUNK_FACTOR`).
- `each(chunkPolicy, …)` and `range(chunkPolicy, …)` use balanced distribution: first `extra = total % effective` chunks get `base+1`, the rest get `base` (where `effective = chunkPolicy.resolve(total, workers)`). Don't replace with simple ceiling-division — the case `total=15, N=14` where ceiling collapses to fewer chunks than requested is what motivated the formula.
- `ChunkPolicy::resolve` normalises an exact `0` to `1` and clamps to `[1, total]` (single chunk over the whole range when 0/1); together with the `count==1` inline path in `runQueueJob`, that's the historical "serial fallback" semantics. The previous `min(max(taskCount,1), total)` clamp in `makeSetup` now lives in `resolve`.
- `task.h` lives at [include/multi/details/task.h](include/multi/details/task.h) — internal-only. Users go through `multi::async`/`parallel`/`each`/`range`; they should never include `Task` directly.

### When extending

- New synchronous primitives belong as new `Job` subclasses in [details/job.h](include/multi/details/job.h) plus a thin 2-line dispatcher in [context.inl](include/multi/details/context.inl) (`construct Job, call runQueueJob(job)`) and a forwarder in `multi.h`. Don't add new dispatch shapes by building task vectors in `Context` — the architecture is "Context is thin, Jobs own their setup".
- New `Job` subclasses must override `run(std::size_t i) noexcept` non-virtually, and use the inherited `runOne(...)` for the try/catch + decrement pattern. Don't reinvent it. The `m_remaining` release in `runOne` is what publishes `m_firstException` to waiters via `remaining()` — preserve that pairing.
- `async` is the exception: `AsyncJob` is not a `Job` at all — its exception path is the promise, and it doesn't go through `runQueueJob` (lifetime extends past the caller's stack frame, so it's heap-allocated via `shared_ptr`). Don't make it derive from `Job` again: every async allocation would carry a countdown, `once_flag` and `exception_ptr` it never uses. `RecipeJob` is the same kind of exception (see Recipe).
- Every wake goes through `workerNotify` (lock, claim if parked, unlock, notify only if claimed). A new push site must wake after pushing, or a task can sit behind a busy worker while the others sleep: a single push calls `wakeAfterPush(idx)`, which is `anyParkedAfterPush()` and, if that returns true, `workerNotify(target)`, then `wakeOneParked` if that claims nothing (target busy) or the push was the owner's own; a batch does the same once per batch, as `submitBatch` does. A new park path must register as parked and fence before its last re-check, and never `cv.wait` unregistered. Keep `tryGetTaskBeforePark` a single pass.
- Don't drop the `bool isActive()` inline-fallback path on `WorkerPool::submit*` — it's the single-threaded story. Don't drop the `count==1` inline-fallback path in `runQueueJob` either — it's the chunked `taskCount<=1` serial story, and `multi::Serial`'s order guarantee rests on it.
- `WorkerPool::~WorkerPool` asserts `stop()` was called explicitly; release builds clean up defensively but the assert is the contract.
- New owner-side push sites must use `tryPushLocal`; cross-thread pushes use `tryPushRemote`. Route new push sites through `pushOrRun` — it handles the owner/non-owner split and runs the task inline when the deque is full.
- New `T` types stored in `ChaseLevDeque` / `MpmcQueue` must be nothrow-move-assignable, nothrow-move-constructible, and default-constructible (`static_assert`s in the headers will catch this). The Chase-Lev claim-first steal relies on the per-slot sequence release ordering — don't switch back to a read-then-CAS algorithm without first switching `T` to a copy-supporting representation.
- **Don't add a Context back-pointer to `Handle`.** The Context-agnostic design is intentional and was the conclusion of a deliberate refactor: it lets Handles cross context boundaries, removes the include cycle between handle.h and context.h, and makes the steal-participate behaviour an explicit, visible call (`waitAll`) instead of implicit. If you find yourself wanting Handle to "just know" the right context to steal from, write a `Context::waitUntil(pred)` predicate primitive instead.
- **Don't add a way to copy a `Handle` or expose its `shared_future`.** `take()` moves the result out of the shared state, which is safe only because the Handle is that state's sole reader: it is move-only, nothing exposes `m_handle`, and `Context::async` moves in the only `std::future` for the state.
- New waits go through `Context::stealUntil` so they keep the backoff; don't write another `while (!done) tryRunSteal();` loop.
- **Caller-stack growth from steal participation is real.** When the calling thread sits in `runQueueJob`'s wait loop and steals child tasks, each stolen task that itself dispatches via `parallel`/variadic `async` adds another frame to the caller's stack. The library currently ships no recursive parallel primitive, but if you add one, bound its recursion depth in terms of *worker count*, not input size — a fixed cutoff that yields `log₂(n / cutoff)` depth will overflow the stack under ASan / on small thread stacks for large inputs. Cap depth at `~log₂(workerCount · k)` so the split count tracks the pool rather than `n`, or rewrite the recursion iteratively (a `while` loop over a work list) so the stack bound is constant regardless of `n`.
- **OS-specific calls go in [src/platform.cpp](src/platform.cpp)**, declared in [details/platform.h](include/multi/details/platform.h): `setCurrentThreadName`, `preciseSleep` and `threadCpuTime` (which only the tests read). It is the one library source that includes `<windows.h>` or `<pthread.h>`, with `WIN32_LEAN_AND_MEAN` / `NOMINMAX` defined under `#ifndef` so a consumer's own definition cannot raise C4005. Add a new call there rather than putting an `#if defined(_WIN32)` in the code that needs it, and keep platform code out of the tests — the one exception is the thread-name read-back in [test/workerpool.cpp](test/workerpool.cpp), which calls `pthread_getname_np` directly.
- New threads created outside `WorkerPool::start` (if any) should call `details::setCurrentThreadName(name)` inside their thread function with a short ASCII name — workers self-name as `multi-N` from inside `workerMain` so they show up identifiably in `top -H` / Activity Monitor / Visual Studio. It is platform-conditional (`SetThreadDescription` on Win10+, `pthread_setname_np` everywhere else) and best-effort; failures never propagate.
- The free-function layer in `multi.h` is a thin forwarder over `multi::context().method(...)`. Every new public Context method needs a matching free-function wrapper there; otherwise users on the global context can't call it.
